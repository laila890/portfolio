Notes from production

Three write-ups on the work behind this portfolio: a migration, a deploy pipeline, and how I chase down bugs.

AWS Migration RDS S3 CloudFront

Why it moved. The CRM backend started on Supabase. The goal of the move to AWS was scalability: more control over the servers, the database and the delivery layer as the product and its traffic grew. I led this migration at VigoMerge.

How the pieces map. The database became PostgreSQL on Amazon RDS. Storage uses S3, with CloudFront for content delivery. The Node.js backend runs on EC2 behind Nginx, with PM2 keeping the process alive and restarting it if it crashes. Cloudflare sits in front for DNS, SSL/TLS and CDN.

A simplified view of the stack, not a full network diagram.

What changed in deploys. On a managed platform, deploys are mostly handled for you. On EC2, they are something you own. I set up GitHub Actions and Docker so that every release is built and deployed by an automated pipeline, not by hand on the server.

What a move like this has to get right. Copy the data and check it before switching traffic. Move every connection string and secret to the new setup. Give each service only the IAM permissions it needs, and keep the database private. Turn on CloudWatch logs and metrics before launch, so problems show up in your dashboards before they show up in support tickets. And keep a way back until the new system has proven itself.

CI/CD GitHub Actions Docker EC2

The goal. A release should be the same every time, whoever pushes it. Manual deploys drift: someone forgets a step, a server has a different version, and nobody can say exactly what is running.

The flow. A push to the main branch starts a GitHub Actions workflow. The workflow builds a Docker image, so the app runs with the same dependencies in testing and in production. If the checks pass, the new version is deployed to the EC2 server, where Nginx receives the traffic and PM2 keeps the app running.

A simplified example of the shape. This is a generic outline, not a copy of the production workflow:

on:
  push:
    branches: [main]
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: docker build -t app .
      - run: # run tests
      - run: # copy to the server and restart

What it gives. Every deploy leaves a record in the Actions tab. A failed build stops before it reaches users. And a release that once needed someone at the terminal becomes a push to main.

Troubleshooting CloudWatch Testing HP-ALM

Reproduce it first. A bug I can't reproduce is a guess. I get the exact steps, the user role, the input and the environment, and make it fail on demand. Then I know any fix can be checked against something real.

Read the evidence. On AWS, CloudWatch logs show what the application said at the time, and metrics show what the server was doing: CPU, memory, errors, response times. I line these up with the moment the problem started, and ask what changed around then: a release, a configuration value, a data change or a dependency.

Fix the cause, not the symptom. A restart can clear an error and leave the reason behind. The aim is the underlying cause, so the same incident doesn't come back. This approach, with defect tracking and root cause analysis in HP-ALM, helped cut system downtime by 20% at InovaAntage Systems.

Test before release. A fix gets tested against the original steps, then against the flows around it: API calls, payments (PayU) and role-based access, since a change in one place often breaks another.

Write it down. Each change gets documentation in technical and plain language, so management can review it before and after release, and the next person can see what happened and why.
